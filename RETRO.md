## 1 - Slash command value
The "\scaffold-endpoint" saved the most prompt writing effort (COMMAND_LOG.md, row 2: `tags post`, stayed in scope). Writing the same thing as a prompt would take about fifteen lines every time. I would have to name the route, service, and schema files, explain that the canonical "routes/tasks.py" pattern actually lives in routes/api.py, forbid logic in the route, require test-first, list the expected 201 and 422 tests, and say how to check scope. I would also have to remember the two lessions from my first version: calling ".get()" on the body in the route caused a 500 on non-object JSON, and "git diff --stat" missed the three new untracked files. My PLAN_LOG shows I did not remember lessons like these in prompts. In sessions 3 and 4 (from PLAN_LOG) I re-amended the same lint rule because a fresh session repeated the old mistake. The command is better because a fix made once stays in the file. The next endpoint costs two words instead of a page of prompt.

## 2 - Hook reliability
Both bypass vectors got past the hook before I fixed it (HOOK_LOG.md, rows 1 and 2). In Vector 1, an Edit on `Utils/errors.py` changed the real `utils/errors.py`, because the path check was case-sensitive and Windows paths are not. Vector 2 was worse. Bash was already in the matcher in settings.json, yet `echo "# vector 2 test" > utils/errors.py` overwrote the whole protected file and deleted all three error classes. The Bash branch only looked for `rm -rf`, `DROP TABLE` and force-push, and never checked which file a command wrote to. Drill 2 showed the same gap earlier: with a `Write|Edit|MultiEdit` matcher, Claude appended to `utils/errors.py` with `cat >>` and the hook never ran. My first Vector 1 attempt also showed Claude editing `guard_writes.py` itself without being blocked. All of this shows that "the rule is in settings.json" only guarantees the hook runs. Enforcement is only as good as the hook's model of every way a tool call can reach a file: letter case, Bash redirects, `sed -i`, Python writes, and the hook's own file. Until each of those was covered, check_guard.py was at 22/28. Some blocks I counted as "enforced" were really Claude choosing to comply. After `rm -rf` was blocked in Part A live check 1, Claude said it could have used `Remove-Item -Recurse -Force` and chose not to, and my hook would not have stopped it.

## 3 - dvisory vs. deterministic
The rule "For existing tests in tests/test_tasks.py never edit or delete them" is still advisory in my CLAUDE.md Do-not-touch section. I didn't add it to the hook because the hook blocks at the file level, and this file must stay writable. `/fill-tests`, `/scaffold-endpoint` and `/audit-errors` all append tests to it (COMMAND_LOG rows 1-3), so adding `tests/test_tasks.py` to BLOCKED_PATHS would break all three commands. Enforcing the rule properly needs a content check that compares old and new versions of the file, not a path check. I will move it into the hook as soon as either of these happens. First: any logged session shows a `-` line inside an existing `def test_` function in "git diff tests/test_tasks.py", meaning Claude modified an existing test even once. Second: I have written an AST check for the hook that parses the old and new file and exits 2 if any existing `test_*` function is missing or its body changed, and it passes check_guard cases for "append a test" (allow) and "edit an existing assert" (block). So far all three commands have only appended, which is why the rule is still advisory.

## 4 - Limits of hooks
I wanted to enforce the CLAUDE.md rule "Perform a quick test run after each file edit: "pytest -q" and "Run "pytest -v" and "ruff check ." before finishing any task." I couldn't do it with PreToolUse. A PreToolUse hook runs before the edit and can only allow or block it. It can't know whether the code will pass once the edit is applied, and it can't make anything happen afterward. The rule is about what happens after a change, and about the end of a task, which is not a tool call PreToolUse could block. My evidence that the rule needs enforcing: in Drill 1 v1 I couldn't tell whether Claude ran pytest after each function, and in PLAN_LOG Session 3 Claude skipped the planned final "pytest -v". The right mechanisms are a PostToolUse hook on `Write|Edit|MultiEdit` that runs "pytest -q" after every edit to `services/` or `routes/` and reports failures to Claude, and a Stop hook that runs "pytest -v" and "ruff check ." when Claude tries to finish and blocks it if either fails. The same limit applies to my content guard. Claude pointed out that `os.environ.get("DATABASE_URL", "sqlite:///tasks.db")` would be blocked, because a regex matches text, not intent. Telling a hardcoded secret from a harmless default needs a human reviewer or a semantic check, not a pattern match.
